# BlindPass threat model

**Aligned to source:** 2026-09-23; Rust controller section 2026-09-25; legacy SPS removal reflected 2026-10-07. This replaces the March threat-model snapshot in the Obsidian vault as the current interpretation. Existing TM-001–TM-007 identifiers are retained. The update inspects selected code paths; it does not rerun the original audits or public deployment probes.

## Scope and trusted endpoints

The Rust controller, browser input, operator console, gateway, agent runtime and OpenClaw paths are in scope. The legacy SPS server, the hosted dashboard and the billing, guest-intake and x402 payment code were removed on 2026-10-07 and are in git history before the removal commit. Rows below that described them keep their 2026-09-23 record and say they were removed with the legacy stack; the removal upgrades no finding. The host broker has a selected real-VM P01 profile. The Rust controller is implemented and tested locally but not accepted or deployed; fleet authorization and browser operation remain proposed boundaries. P01 evidence does not establish a complete supported-host matrix or product acceptance.

Protect source credentials, access/refresh tokens, bootstrap API keys, signing keys, secure-input links, recipient-key integrity, workspace policy and authorization/audit state. The browser handling input and the recipient decrypting it are plaintext endpoints. HPKE protects the relay path only when endpoint code and recipient-key binding are trustworthy.

An authorized process receiving a credential can read/copy it. The proposed browser mode intentionally hands session authority to the agent. A short controller retrieval TTL or broker grant does not shorten a static provider key's lifetime or revoke a website session. See [mode/revocation contracts](https://github.com/tuthan/docs-vault/blob/main/blindpass/docs/product/Specification.md#consumption-modes).

## Authentication storage

Source: [controller session routes](../../crates/blindpass-controller/src/routes/admin_session.rs), [console API client](../../packages/console/src/api/client.ts), [browser requests](../../packages/browser-ui/src/app.js). The SPS auth routes and the dashboard `AuthContext` that this section first described were removed on 2026-10-07.

| Mode/path | Actual behavior |
|---|---|
| Operator console (P04) | `HttpOnly` `SameSite=Strict` session cookie (`Secure` when the public URL is HTTPS), a refresh cookie scoped to `/api/v3/admin/session/refresh` and a session-bound CSRF token. The console stores no credential in web storage ([finding F-8](finding-disposition.md)) |
| Hosted SPS and dashboard modes | **Removed with the legacy stack 2026-10-07** [original status: open]. The 2026-09-23 record: hosted non-test responses set `sps_refresh_token` in an `HttpOnly`, `SameSite=Lax` cookie at `/api/v2/auth` and omitted the raw refresh token from JSON; hosted `NODE_ENV=test` and non-hosted responses returned it in JSON; a body token took precedence over the cookie on refresh; the dashboard kept its access token in memory but wrote a returned refresh token to `localStorage`, and `clearAuth()` did not remove it |
| Browser input | Since P04 slice 9 the input page has no session or refresh path: signed-link requests send no cookies (`credentials: "omit"`), and the page stores only the language preference. On load it removes a `blindpass_refresh_token` left in `localStorage` by the earlier page on the same origin |
| Desktop approval app (P04-D3) | Separate Quickshell process. Desktop login (`kind: "desktop"`, no `Origin`) returns a bearer access token and a refresh token in JSON and sets no cookie. The access token stays in memory and the controller refuses it 20 minutes after issue; the refresh token is in `$XDG_RUNTIME_DIR/blindpass/session` (0600) and rotates on start and every 15 minutes. The bearer reaches only session read/refresh/logout and `/api/v3/approvals`. Any `Origin` sends a request down the cookie path, so page script can't use a desktop token. Requests go through curl with redirects refused and system CA/host-name verification. Same-user code can read the refresh file: not an OS boundary |

The earlier claim that refresh tokens were uniformly in `sessionStorage` was incorrect for the 2026-09-23 checkout (it described the removed dashboard). XSS can exercise an authenticated operator's authority even without reading an `HttpOnly` cookie. Browser-session/CSRF-origin behavior and cleanup of a token left in `localStorage` by an earlier page on the same origin need explicit testing (G-1 in the [finding disposition](finding-disposition.md)); do not claim frontend compromise is contained by cookies alone.

## Rust controller (P02, not accepted)

Source: [controller crate](../../crates/blindpass-controller). The rows below are checked by the Rust store and HTTP tests and the contract suite on SQLite and PostgreSQL ([P02 evidence](../testing/evidence/p02-controller-api-migration-rerun.md)); they do not certify a deployment.

| Area | Actual behavior | Residual risk |
|---|---|---|
| Agent tokens | Bootstrap keys are Argon2-hashed and exchanged for HS256 access tokens. External providers need a local JWKS file and pinned issuers and audiences; tokens must carry `exp`, `iss` and `aud`, and expiry has no leeway | An access token stays valid until it expires after its key is rotated or revoked. `nbf` and SPIFFE claim contents are not checked |
| Tenant scope | Tokens asserting another workspace are refused on secret-request and exchange routes, including one whose subject collides with a tenant agent | One tenant per database |
| Operator sessions | Passwords are Argon2-hashed. Refresh tokens are SHA-256-hashed, rotated, and a replay revokes the whole family. Mutations need the CSRF header. Session creation and password changes apply only while the verified password hash is current | The `bp_session` cookie carries the raw session identifier and the CSRF secret is stored as issued, so database read access exposes live sessions. No login throttling. Refreshing extends a session family without an absolute limit. Temporary passwords do not expire |
| Rate limits | Authenticated secret-request creates and exchange-request attempts have independent atomic per-agent, per-tenant windows (default 60 calls per 60 seconds); token minting remains limited per client IP | Limits are local to the controller database and do not add hosted billing quotas. Metadata audit records the first excess call in each window without request or secret values |
| Audit | Metadata events for agent token mints, rate limits, exchanges, approvals and clock reconciliation | Secret-request lifecycle and administrator changes to operators, agents and policy are not audited |
| Clock | A one-second monitor compares database and host wall time against monotonic elapsed time; startup also checks persisted Linux boot identity and boottime. Regressions beyond the configured 2-second default tolerance set a durable fence | A boot change or unreadable boot ID fences the controller and purges transient authority. Operator reconciliation also revokes sessions. Agent JWTs and signed links use the host clock and retain their own token expiry behavior |
| Transport | Plain HTTP, loopback by default; TLS terminates at a reverse proxy (P02-D7) | Production proxy deployment is unverified until P06 |

## Threat register

| ID | Abuse path and impact | Current control/boundary | Remaining work or evidence |
|---|---|---|---|
| TM-001 | Signing-key compromise or configuration regression permits forged user/agent/fulfillment authority | Required-secret checks and token scope/workspace validation (the SPS implementation was removed 2026-10-07; the controller refuses missing or unsafe keys at startup) | Protect/recover/rotate deployed keys; retain fail-closed regressions. A compromised controller remains an authorization risk |
| TM-002 | An official input link redirects credential submission through attacker-controlled API/key metadata | Query-controlled API origin removed | Keep origin/key-substitution regressions; trusted input code and recipient-key binding remain necessary |
| TM-003 | Frontend compromise steals a body/legacy refresh token or exercises authenticated authority | Console: `HttpOnly` `SameSite=Strict` cookies, session-bound CSRF and no web storage (finding F-8). SPS hosted cookie delivery and the dashboard's in-memory access token were removed 2026-10-07 | SPS and dashboard `localStorage` compatibility, body-token precedence and cleanup gaps: removed with the legacy stack 2026-10-07 [open]. Test migration, logout and origin/session behavior on the console |
| TM-004 | Logs/artifacts disclose secure links, codes, tokens or credential values | Runtime logging redaction/opt-in controls were reported in March | The demo scripts (removed 2026-10-07) printed dummy values and could not prove runtime secrecy; inspect actual client/log/artifact paths and restrict sensitive evidence |
| TM-005 | Public guest requests or repeated approvals exhaust quotas, queues or operator attention | Existing rate limits and policy/approval checks. The SPS guest-intake surface was removed 2026-10-07 | Guest-intake protections: removed with the legacy stack 2026-10-07 [open: maintain while expansion is frozen]. Pilot must measure approval fatigue and preserve bounded grant scope |
| TM-006 | Same-origin script compromise abuses input/console sessions (and, before its removal, dashboard sessions), worsened by permissive CSP | Controller-set CSP and frame protections on the embedded console and input page, and the input-page nginx template (findings F-9, F-11). The dashboard nginx CSP was removed 2026-10-07 | The dashboard's permissive `connect-src`: removed with the legacy stack 2026-10-07 [open]. Validate actual deployed headers, and retain session authority/XSS limits; cookies do not stop all authenticated actions |
| TM-007 | Compromised facilitator/payment trust causes fraudulent acceptance | Historical atomic settlement ownership reduced local duplicate-settlement races | **Removed with the legacy stack 2026-10-07** [original status: frozen payment-surface backlog]: the SPS settlement code and the x402/viem client code are gone. No payment audit was done, and none is implied |
| TM-008 | A local process spoofs a systemd routing name or reuses a PID/invocation to obtain another workload's credential | Proposed root-only loader socket plus pidfd-based unit/invocation authentication | W0 real-systemd tests, including known forged-name regression; user-manager/shared-UID delivery excluded |
| TM-009 | Controller/key substitution or copied grants redirect provisioning across nodes/workloads | Proposed verified recipient binding, enrollment lifecycle, local ceiling and scoped grants | Fleet E/I/C scenarios; ciphertext-only storage is not proof against controller compromise |
| TM-010 | Agent accesses private login state or receives more cookies/storage than approved | Proposed account/process separation and fresh-context cookie allowlist | Browser B-I14/B-I15; no general confinement claim for unrestricted browser tools |
| TM-011 | Handed-off session creates lasting account authority or survives cancellation | Proposed restricted application role, non-extendable lifetime and server revocation | B-E12/B-E15/B-E16/B-E17; reject applications that cannot enforce these prerequisites |
| TM-012 | Broker/socket failure starts a service with missing/partial credentials; copied provider key survives grant expiry | Proposed explicit consumer validation and separate provider-revocation status | C04/C12/C13; service delivery trusts the consumer and cannot recall copies |
| TM-013 | Controller partition, stale restore or competing restored instance revives revoked/consumed authority | Proposed expiry/reconciliation, protected key backups and single-controller fencing | E07, O-series and D-series in both deployment profiles |
| TM-014 | Browser login page or deployed application itself captures the source password | The credential receiver is a trusted endpoint | B-E14 boundary demonstration; do not let agent-controlled code modify the approved login endpoint |

## Evidence and follow-up

The [pilot test catalog](https://github.com/tuthan/docs-vault/blob/main/blindpass/docs/testing/Linux%20Fleet%20Pilot.md) owns scenario detail. S-series covers W5 regressions; B-series covers mode-1 browser handoff; fleet E/I/C/O/D covers identity, service delivery and deployment. Existing repository test locations and flags are in [testing setup](../testing/README.md).

Resolve audit items by identifier and evidence date. This update corrects F-7/F-8 documentation and v2 M-2/M-3's current interpretation (M-2/M-3 concerned the SPS email tokens, removed 2026-10-07); code/test/deployment follow-up remains explicit. Confirmation codes, storage cleanup, client timeouts, origin restrictions, deployment hygiene and active-path exposure risks stay in W5. The frozen guest and payment risks (TM-005's guest half, TM-007) were removed with the legacy stack on 2026-10-07, and the finding disposition records them as such rather than as closed.

Actual host isolation, MCP-client handling, server-side website revocation and deployment parity have not been executed here. Local scans and documentation review cannot establish those guarantees. See [security references](README.md) for the dated reports.
