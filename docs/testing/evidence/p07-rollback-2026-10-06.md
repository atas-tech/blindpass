# P07-E03 evidence: rollback rehearsal on the packaged native controller (workstream H3)

**Date:** 2026-10-06
**Verdict: P07-E03 is NOT PASSED.** Nine of the ten required observations were made on both guests. The tenth, "the previous
service is restored", failed in the part that matters for a release: the shipped native installer has no way to put the previous
**program version** back. State, identity, lifecycle, sessions, single issuer, lockout recovery and the revoke step all behaved
as the procedure says.
**Scope:** `docs/release/rollback.md` steps 2, 3 and 5 (plus the stale-state refusal) on disposable real-systemd guests, Ubuntu 24.04
and Debian 12, SQLite controller store. Status words are literal: **Observed** = the guest printed it in the run quoted;
**Not run** = no result exists.

## Stand-ins (read before the results)

- No earlier packaged release exists. "Previous" is the 0.1.0 archive under test; "candidate" is the **same verified binaries
  repacked as 0.1.1** with the schema unchanged (a changed `manifest.json` version only). So no automatic pre-upgrade backup
  exists, the operator takes one by hand, and the rehearsal cannot show that two different builds interoperate. In particular
  "the restored controller runs the installed program" is true of any restore, not only of this stand-in.
- The authority is the guest's own PostgreSQL (not independent). No real node exists; one broker-trust row was seeded in the
  authority and covered by a named waiver.
- A defect is declared, not injected: the candidate session is treated as suspect.

Other facts observed on both guests: a node trust row that could not report had to be waived and ended `revoked` (a restore-based
rollback revokes trust of nodes that do not report); the restored controller's review listed only `{"operator": 1}`; the uninstall
removes the previous program tree as well as keeping the installed version's record.

## Probe: can the previous program be put back with shipped tools?

RB08 purged the installation, installed the 0.1.0 archive fresh and tried the restore with the 0.1.0 restore unit. Both guests:
`P07-RB08 stopped_at=restore_with_the_previous_release_restore_unit ... marker_initialized=False initialized_file_present=False
restore_unit_condition_result=no restore_unit_state=inactive`. `blindpass-controller-restore.service` and
`blindpass-controller.service` both carry `ConditionPathExists=/etc/blindpass/controller-initialized`; only `install.sh --initialize` writes it, and
that creates a new database (it needs the empty data directory and freshly initialized keys), so a restored installation can neither
start nor be upgraded through the installer without hand-made root files and an edited install record. This was **not** tried further:
the hand-edit route is not a procedure the product supports.

## Corrections this rehearsal made to `docs/release/rollback.md`

1. Step 2 said "the previous archive can be reinstalled". On native that is refused. Rewritten, with what the installer does allow
   (same-version reinstall over retained state) and what Compose is expected to allow (not rehearsed).
2. Step 3 said "use the automatic pre-upgrade backup that `migrate` published". That exists only for an older schema; a same-schema
   candidate takes none. Added a before-upgrade backup step and stated the rollback point.
3. Step 5 named the recovery review commands but not how to revoke sessions. Added `reset-password <username>` (rehearsed) and the
   lockout recovery, noted `reconcile-clock` is not a general revoke, and listed `blindpass admin node revoke` as not rehearsed.
4. The skeleton said the rehearsal was not run and that no mechanism was added. Now records the result and the open owner decision.
5. `docs/deploy/upgrade.md` and `docs/release/known-limitations.md` now state that a native upgrade has no way back to the previous
   program.

## Not run

- A genuine earlier release (two different builds); a schema-changing candidate and its automatic `pre-upgrade-*` backup used as the
  rollback point; the PostgreSQL controller store; Compose rollback and the Compose image-tag route; a node package or a real node
  reporting during recovery; the distribution steps in step 1 (GitHub release, image tags, `npm deprecate`);
  `blindpass admin node revoke`; hosted CI.
- The first two runs of the new mode (earlier the same day) ended at RB08 with an unhandled `FileNotFoundError` because the probe was not
  yet tolerant of its own blocking step; their required observations were identical. They are superseded by the final runs above.

## Owner decision (confirmed by the owner 2026-10-07)

Accept roll-forward plus restore-based **state** rollback for the pilot, and say so wherever a "previous release restored" guarantee could be
read; the first release has no previous release, so this does not block 0.1.0. Before a second release ships, either keep that
position or add an installer path that adopts a restored installation (a downgrade/adopt flag with its own ADR and rehearsal). Nothing in
this change adds such a path.
