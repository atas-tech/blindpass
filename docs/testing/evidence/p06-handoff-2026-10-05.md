# P06 planned same-owner handoff (slice 8, P06-D28) — 2026-10-05

**Status:** component, QEMU/KVM and Compose evidence on the uncommitted tree above `8a595ad`. It implements the owner decision P06-D28 (planned handoff; restore stays the disaster-recovery path). Runbook: [handoff](../../deploy/handoff.md). It does **not** establish P06 acceptance, RC09-RR05, a native-package handoff or a native↔Compose handoff. Nothing here is committed.

## Built

- `blindpass handoff export | import | abort` (co-located CLI forwarding to `blindpass-controller handoff …`, `crates/blindpass-controller/src/handoff.rs`). SQLite only; no schema bump.
- `export`: needs a `fenced` record and a stopped service, takes the existing maintenance claim, seals the existing authenticated archive (`create_backup`, unchanged), writes the retirement marker `handoff-marker.json` (0600) next to the database and a receipt `handoff-<id>.json` beside the archive. Repeating the same id re-verifies the archive digest and recreates the receipt; another id is refused while a marker exists.
- `import`: verifies receipt, archive name/digest, signature and manifest (SQLite, exact current schema, tenant, issuer key, `recovery_generation` = receipt epoch), then requires the authority record `fenced` at the receipt's epoch and revision; publishes `keys/` and `data/controller.db` plus a destination marker into a new private root. No recovery reservation, no invalidation, record unchanged.
- `abort`: removes the marker (and this handoff's receipt and archive with `--output`) only while the record is still `fenced` at the exported revision; refuses afterwards (rollback is restore-only).
- Startup guards (`store/ownership.rs`): a retired source refuses `serve`, `migrate` and `reconcile-clock` (`handoff_retired`); a destination's first start needs exactly revision R+1, a later start after an attempted first start any higher revision (`handoff_stale` otherwise); the marker is consumed after the store opens.
- `deploy/controller/compose.handoff-sqlite.yml` (opt-in `handoff` profile: export, abort, import, install), `compose-up.py --scenario handoff`, `tests/fleet/p06-handoff-vm.py`.

## Bugs and harness errors found and fixed

- **Gate could pass for the wrong reason (VM H8):** the first version passed `status --nodes --require-online` 0.6 s after the destination started because the node's last-seen from the previous holder was still inside the 45 s window. The gate now needs every active node's last-seen to be later than the destination's start.
- **Wrong assumption (VM H12):** a stopped destination restarts without an activation. It does not: every start consumes a revision (D12/D17). The scenario now activates before each restart, which also makes the stale-source marker check meaningful (an active, unheld record is the only state in which the marker, not the ledger, is the refusal).
- **Install job (Compose H3):** `ls -A /keys /data` prints directory headers, so the "volumes are empty" check refused every install. Fixed to test each directory separately; found only by the real gate.
- **Overlay render-time variables (Compose):** the overlay requires its variables even for inactive profiles, which made the harness's expected-failure `check-config` run fail before creating the network and the authority container fail to start. The overlay is now included only in the handoff scenario, with placeholders until the real directories exist.
- Harness: the authority container needs an explicit address on the second project's network (the controller's reserved address was taken); the disposable 10001-owned transfer and staging directories needed the same ownership hand-back as the other fixtures.
- **Design finding:** an interrupted export (killed after the archive was sealed, before the marker) leaves one unreferenced sealed archive that `abort` cannot know about. Documented in the runbook; the VM scenario asserts it and removes it as an operator would.
- **Data-loss incident outside the repository (my error):** while recording the aarch64 section I ran `open(p,'w').write(open(p).read()…)`, which truncates the file before reading it, on the vault plan `docs-vault/blindpass/docs/product/phases/06-deployment-and-recovery.md`. ## Limits

- **Native package and native↔Compose handoff were not run.** The native profile has no handoff units; the commands were run only as host processes and as Compose jobs. The native VM authority is an in-guest PostgreSQL, so a shared authority between a native guest and a Compose project does not exist in the current harness. The archive layout is the same for both profiles, but that is design, not evidence.
- SQLite only. PostgreSQL controllers share one database; `export` refuses them (HO07), and a two-PostgreSQL-controller move was not run.
- One node, one broker, one grant per side. No second broker, no multi-node reconnect timing, no DNS or load-balancer cutover; the QEMU scenario moves the controller on the same host and port.
- The `blindpass handoff` CLI wrapper was exercised in the VM and Compose runs; the controller binary was invoked directly only for the failpoint cases.
- The failpoint binary (`--features p02-test-failpoints`) is used only for H1a and H7a; the other steps run the release build.
- Clock skew across hosts (a destination behind the source's last write) was not exercised.
- The recovery key still both signs and decrypts the archive (ADR 0010 split is the next task); the transfer package is only as safe as that key and the archive together.
- The native VM matrix, `p06-relay-vm.py` and the aarch64 build were not rerun for this change unless listed under "Final run".
- Acceptance and RC09-RR05 remain false.
