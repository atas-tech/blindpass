# P06 PostgreSQL restore and upgrade — 2026-10-05

**Status:** component, in-image and Compose evidence on the uncommitted tree above `8a595ad`. Builds on the [PostgreSQL backup record](p06-postgres-backup-2026-10-04.md) (ADR 0011). This closes the PostgreSQL restore and PostgreSQL upgrade refusals. It is not a complete recovery workflow, a real-host rollback rehearsal or P06 acceptance (all still false).

## Built

- **Restore:** `blindpass[-controller] restore` takes `--database-url-file` for a PostgreSQL archive ([guide](../../deploy/recovery-stage.md#postgresql-archives)). The target must be an empty database (no user schema, nothing in `public`). The pinned `pg_restore` runs as one transaction; the restored schema is re-measured against the authenticated manifest, bound to the `recovering` authority record, invalidated by the same store code as a SQLite restore, and only then are the controller keys published (`keys/`, `restore.json`, no `data/`). Failure before publication drops only the schema this command restored. The argument form must match the archive's backend.
- **Older schemas:** the PostgreSQL snapshot measurement now accepts a supported older schema (16 up to the current schema), requiring only the tables and columns introduced up to it, so a pre-upgrade backup can exist. A restore of such an archive migrates it forward in the empty target.
- **Upgrade:** `migrate --pre-upgrade-backup-dir/--recovery-key-file` now upgrades a PostgreSQL store the same way as SQLite: verified encrypted pre-upgrade backup first (pinned toolkit), then migration. Without the toolkit (a host) it refuses unchanged. Compose: `deploy/controller/compose.upgrade-postgres.yml` (`upgrade` profile).
- **Shipped-profile finding fixed:** the PostgreSQL Compose profile kept the controller in `public`, which the backup refuses. My earlier PGC harness hid this by creating a `controller` schema and a URL option by hand. The profile now mounts `deploy/controller/postgres-init/10-controller-schema.sql` into the official first-initialization hook (dedicated `controller` schema, set as the role's `search_path`). A pre-existing `public` store needs a documented one-time move (see the Compose quickstart); that move was not run against a real deployment.
- **Test infrastructure:** the authority driver gained `--test-target restore_postgres` and `--in-image` (runs the Cargo target inside the pinned-toolkit image with host networking, values passed by environment name); the `pgtest` stage prebuilds its test targets; the toolkit fixture moved to `tests/pg_fixture/`; the credential watcher excludes the test's own process tree and checks environments only for product tools.

## Limits

- Restore is the empty-target, fenced stage only. Source-stop proof, node reconciliation through the relay, provider review and activation remain open (RC09-RR03..RR05); a restored PostgreSQL controller was only started to confirm it stays fenced.
- No real-host or VM run of a PostgreSQL rollback (upgrade, then restore the pre-upgrade archive into a fresh database, then reconcile). RP05 covers the restore half and UP13/Compose the upgrade half separately.
- The native profile stays SQLite; the native VM matrix was not rerun for these changes (they do not touch the native packaging).
- Restore time was not measured on a large database (small fixtures); the restore deadline is 300 s for `pg_restore` and the publication bound is 360 s.
- x86-64 only; no aarch64 toolkit run; no GHCR publication.
- Restore uses the target role's `search_path` to find the restored schema; a role whose `search_path` does not select the archive's schema fails after the restore and the schema is dropped (RP04), but the operator error surfaces only as the static refusal.
